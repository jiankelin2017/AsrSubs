# ADR-0003 · 版本号重置与三段式规则

| 项 | 值 |
|---|---|
| 状态 | **已接受，现行规则** |
| 决策时间 | 2026-11-01（v1.0.0） |
| 影响范围 | `01_源码\version.txt` 及 5 处注入点、安装包命名、CHANGELOG |

## 一句话摘要

版本号从 4.8.26 直接重置为 1.0.0，此后按「主.中.次」三段式递增，4.x 编号全部作废。

## 当前有效结论

- **决策**：小更新动最右位、重要更新动中间位并把最右归零、超大型更新动最左位并把后两位归零。
- **状态**：已接受的现行规则，2026-11-01 确立，当前版本 1.2.0。
- 历史 4.x 记录保留原编号，不得「换算」成 1.x。

## 关键变更（仅影响使用的里程碑）

- 2026-11-01：版本号从 4.8.26 直接重置为 1.0.0，启用三段式规则；旧「次版本 +1 / 主版本 +1」规则作废。
- 2026-11-05：当前版本 1.2.0；固化为 ADR-0003，`..\guides\guide-release.md` 的命名规则以本决策为准。

## 背景

界面迭代期（v4.2 ~ v4.8）每修一处就发一个补丁号（4.8.4 / 4.8.5 / 4.8.13 / 4.8.14 …），到 4.8.26 时版本号密度过高，且「次版本 +1 / 主版本 +1」的旧规则无法区分修补、成组功能与架构变更。

## 决策

**`4.8.26` 直接改名为 `1.0.0`**，此后统一三段式 `主.中.次`：

| 变更类型 | 动哪一位 | 例子 |
|---|---|---|
| 小更新（修补、文案、单点修复） | 最右 | `1.0.0 → 1.0.1` |
| 重要更新（成组功能、体验优化、较大修复） | 中间，最右归零 | `1.0.1 → 1.1.0` |
| 超大型更新（架构调整、不兼容变更、重大重构） | 最左，后两位归零 | `1.1.0 → 2.0.0` |

历史 4.x 记录保留原样不改。`sync_version.py` 不校验格式，三段式写入 5 处均正常（Inno Setup 的 `AppVersion` / `VersionInfoVersion` 也吃三段式）。

## 理由

- 让版本号能表达变更量级，读者一看就知道是小修还是不兼容升级。
- 摆脱「一个补丁号一个版本」的流水账式编号。

## 后果

| 正面 | 负面 / 需遵守 |
|---|---|
| 版本语义清晰 | **4.x 系列版本号全部作废**，任何文档里把 `v4.8.x` 写成「当前版本」都不可信 |
| 便于 CHANGELOG 按量级组织 | 引用历史版本时必须保留原编号（如 v4.8.14），不得「换算」成 1.x |

## 操作 / 参考细节

本决策不提供操作步骤，只列规则落点：

- 版本号唯一来源与五处注入链见 `adr-0004-single-source-version.md`；出包时的命名规则见 `..\guides\guide-release.md`。
- 逐版变更记录见 `..\CHANGELOG.md`；成品命名实例见 `..\reference\reference-release-notes.md`。
- 引用 4.x 历史时保留原编号，不换算成 1.x。

## 失效内容说明

- `archive\archive-dev-doc-20261105.md` §5 的「常规升级次版本号 +1（4.0.4→4.0.5）、大版本主版本号 +1（4.0.5→5.0.0）」**已被本 ADR 取代**，不得再引用。
- §5 中「功能稳定后建议并回次版本（把 4.8.x 归并为 4.9.0）」是重置前的建议，已无适用对象。
- `AsrSubs_v4.8.23_安装器.exe`（重置前成品，2026-11-06 已彻底删除）其安装器逻辑有缺陷（GPU 版可能装成 CPU 版），不要用它装新机器。
